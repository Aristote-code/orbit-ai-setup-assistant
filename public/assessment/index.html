01 / ASSESSMENT DOCUMENTATION

Product rationale

Orbit - AI Project Setup Assistant

Assessment documentation | 18 October 2026 | Working prototype and design rationale

Problem and intended outcome

Project managers need to turn a short brief into a usable project structure without accepting incorrect automated suggestions. Orbit gives them a proposed name, template and tasks, then lets them shape and approve the plan before creating anything.

Core principle: AI proposes. Humans decide.

The supplied conversation describes an assistant that may be correct only around 70% of the time. This is an assessment constraint from the conversation, not a measured result for this prototype. The design therefore makes review explicit and does not display invented confidence scores.

Primary task flow

Describe: enter a brief or choose an example. A separate blank-project route requires only a name.

Review: accept, edit, remove or restore the proposed name, template and tasks. Accepted and edited items enter the included-plan preview.

Confirm: inspect the final included plan, then explicitly create it. Creation is blocked while suggestions remain unreviewed or no name is included.

Continue working: open saved projects, add or edit tasks, mark tasks complete and export a JSON copy.

Scope and assumptions

This is a frontend assessment prototype. Suggestions use deterministic local rules, not a live AI model. Projects and drafts stay in this browser. There is no authentication, server database, shared workspace or collaboration. The original assessment document and submission rubric were not available for this documentation pass; verify the final package against them before hand-in.

02 / ASSESSMENT DOCUMENTATION

Interaction decisions

Preserve the system; adapt the workflow

The first coded version copied the Verification workspace too literally. A narrow central column, repeated project details and duplicate primary actions fragmented a sequential creation task. User feedback prompted a correction: retain the reference typography, rail, icons, borders and AlignUI controls, while using a wider working area and a contextual side preview.

One primary action per step reduces competing paths. The blank route remains an alternative at entry, rather than a repeated side-panel action.

Compact suggestion rows make the whole plan easier to scan. Explicit text states supplement accept, edit and remove icons.

The preview contains only included items. Pending and removed items do not silently become part of the project.

Bulk acceptance affects pending suggestions only. Existing edits and removals remain intact.

Dates start unset. Users add dates deliberately; the prototype does not infer commitments from vague timing.

Returning to the brief preserves the reviewed plan. Replacing it with a new generation requires an explicit choice. Final confirmation remains separate from generation.

Tradeoff: mandatory review adds effort. The hypothesis is that this effort is justified when suggestion reliability is limited. A usability study should check whether users understand and complete the review without blindly accepting everything.

03 / ASSESSMENT DOCUMENTATION

Design system and accessibility

System reuse and provenance

The coded interface reuses the supplied Verification-RSSB project: AlignUI v1.2 Fancy Button, Input, Textarea and Checkbox implementations, the Hugeicons wrapper, Figma-exported SVG assets, and bundled Certia/Cloister fonts. These are reused assets and controls, not an original component library created for Orbit.

Fancy Button: primary, basic, neutral, destructive and success styles, with shared focus and disabled behavior. Orbit mainly uses primary and basic actions.

Input and Textarea: labeled controlled text entry; native date fields in edit dialogs. Checkbox: Radix-based task completion control.

Suggestion rows: product-specific composition in App.tsx, with pending, accepted, edited and dismissed states. This is not a separately published library component.

Core coded colors: interaction #375DFB; border #EBEBEB; body text #333333; secondary text #6C717A. Semantic green, amber and red communicate status alongside text.

Accessibility measures present in the implementation

Visible field labels and accessible names for icon actions. Text labels distinguish review states rather than relying only on color.

Native dialog behavior for modal containment and Escape dismissal; semantic form submission; visible keyboard focus rules.

Loading and toast messages use live status semantics; validation errors use alert semantics. Reduced-motion CSS is included.

Responsive reflow was checked at 390px and 320px during prototype work; the revised review/confirmation layout was rechecked at 390px.

Checks still required

No full WCAG compliance claim is made. Measure text/control contrast, test icon target sizes and 200%/400% zoom, and run a complete keyboard and screen-reader pass. Check focus after step transitions, disabled-action explanations and announcement timing. Figma variable bindings, component variants, auto layout and documentation still need a separate final file inspection against the assessment rubric.

04 / ASSESSMENT DOCUMENTATION

Validation and evaluation plan

Completed technical and interaction checks

Strict TypeScript check and production build pass. The public Netlify page loaded and produced the seven-item supplier-review plan without captured console errors during the deployment check.

Desktop browser checks covered editing a task title and date, removing a suggestion, accepting remaining items and creating the approved project.

The included preview excludes removed tasks. Restoring an item returns it to pending and blocks continuation until reviewed. Final confirmation has one Create project action.

Local draft persistence, saved-project navigation and task completion were checked. Mobile blank-project creation was checked at 390px.

Three automated model regressions pass: a blank project excludes a previously reviewed plan; reviewed creation includes only accepted/edited items and preserves dates; generated items begin pending with no invented dates.

Issue found during documentation

A blank project could inherit accepted suggestions from an earlier plan. The project conversion now treats the blank route separately, returning only the entered name with an empty description, template and task list. A regression test covers that carryover scenario. A browser check also confirmed that switching from an accepted seven-item plan creates a blank project with zero tasks and no inherited template or brief.

Proposed usability study - not yet conducted

Recruit 4-5 people who regularly organize team projects. Ask them to create a supplier review, correct an unsuitable task, remove an unwanted suggestion, set one date and create the project. Then ask them to create a blank project and return to a saved project. Use neutral prompts; avoid telling them which controls to use.

Observe completion without assistance, mistaken inclusions, missed pending items, hesitation at the primary action, and understanding of what will be created.

Record time from brief to confirmed project, review corrections, and confidence in the final plan. Do not treat acceptance rate alone as success; effortless acceptance can hide low-quality review.

No participant research, completion-rate improvement, time-saving percentage or model-accuracy result is claimed. Network failure recovery and backend creation errors are not implemented because there is no backend.

05 / ASSESSMENT DOCUMENTATION

AI usage log and limitations

What AI assisted with

Codex assisted with assessment interpretation, flow proposals, Figma work in the earlier collaboration, reuse of the supplied React components, the coded prototype, debugging, browser checks, the UX critique, deployment and this documentation. This is a retrospective summary of visible collaboration, not a timestamped transcript of every prompt or a complete Figma activity audit.

Human direction and review

The user supplied the Orbit and Align design-system references, requested reuse of the Verification project code and visual language, rejected the initial visual mismatch, identified that the adapted UX felt wrong, and authorized repository creation and deployment. Those interventions shaped both the visual constraints and the later workflow correction.

Corrections made during collaboration

A generic onboarding treatment was replaced with the supplied Verification visual language.

A literal three-column copy was later revised after UX feedback: wider review area, one primary action, project identity and an included-item preview.

Date editing was checked and adjusted to read the submitted date reliably. Regeneration now protects reviewed work, and blank-project carryover has a regression fix.

Prototype behavior versus AI assistance

The design/build process used AI assistance. The shipped assistant itself does not call an AI model: propose() selects local templates using keywords for review, launch, event or general projects. Generic reviews currently share the supplier-review template, so irrelevant suggestions are possible. This limitation must remain visible in a demonstration.

Known limits and next work

No calibrated confidence, retrieval, external context, authentication, cloud sync, permissions or collaboration.

Browser storage can be cleared or unavailable. JSON export is provided; it is not a shared project or an import/restore feature.

A production version needs a server-side generation API, validated structured output, real error/retry behavior, durable storage, permission handling and end-to-end tests.

Review this log before submitting it in your name. Retain the distinction between reused source work, AI-assisted implementation, user decisions and checks that have not been performed.

Suggestion rows expose pending, accepted, edited and dismissed states; edits use a dialog.

Use explicit labels and review-state text alongside action icons and semantic colors.

Include accepted/edited items only; preserve edits during bulk acceptance and allow restoration.

Client explanation - five lines

Orbit turns a brief into a proposed project name, template and task list.

The manager reviews the proposal and controls every included detail.

Accept, edit, remove and restore actions support correction before creation.

A blank-project route and explicit final confirmation preserve choice and control.

This demo uses local rules and browser storage; production AI and cloud services are future work.
